#### 做的还不错的地方

\-01 **文件目录分层清晰,封装到位 **

本次工程在设计文件目录的时候,将代码分层为 

```Plain Text
User/
    Bsp/
    Dev1ce/
    Logic/
    App/
    Ultils/
```

其中不同的功能逐级封装,由头文件中的接口暴露给上级或者同级的其他文件,\(比如将控制GPIO口功能封装成控制LED的函数,使代码中相关区域不会再出现HAL\_开头的接口\)这样,文件本身只需要完成自己该做的操作,在修改代码时不会东一块西一块无从下手\.



\-02 **将各个功能模块的代码在循环里统一调度** 

`main.c`的循环里调用合并了各个功能的`app_task_run();`而各个功能统一调度于`app_task.c`\.

在`app_task.c`中规定了各个功能\(按键,串口,OLED,LED,GIMBAL,TRACK\)的1tick的长度

```C
**#define** KEY_TASK_INTERVAL_MS        10U     /**< 按键扫描周期 10ms */
**#define** LED_TASK_INTERVAL_MS        50U     /**< LED 更新周期 50ms */
**#define** OLED_TASK_INTERVAL_MS       100U    /**< OLED 刷新周期 100ms */
**#define** GIMBAL_TASK_INTERVAL_MS     20U     /**< GIMBAL更新周期 20ms */
**#define** TRACK_TASK_INTERVAL_MS      10U     /**< TRACK更新周期 10ms */
```

统一用"当前时间"的时间戳 `now` 对各任务进行非阻塞刷新,使整体有序易管理

```C
**void** **app_task_run**(**void**)
{
    uint32_t now = HAL_GetTick();
    **if**(now - last_tick_key >= KEY_TASK_INTERVAL_MS)
    {
        last_tick_key = now;
        logic_dev1cePlay_task();
    }
}
```

\-03 **注释齐全格式规范** 

虽然这样的代码看起来会有点像AI写的,但是我认为规范的注释是必要的,文件顶部需要有文件功能说明\.头文件内的接口定义上方应给定接口实现的功能,参数,返回值的含义等\.

事实上:在编写代码的时候\(尤其是工程量稍大时\)很容易忘记之前到底写了什么,在调用接口的时候能快速转到定义看一眼注释就能规避很多东看看西看看但却不知道做什么的便秘场景\.

同样,这样做也便于他人对自己的代码进行修改/拓展\.

**总的来说** :写的多是多了点,但是看着不烧心\.

#### 做的不好或需要改进的地方:

\-01 **光强归一化改进** 

\(依旧疯狂鞭尸追光算法\)

```C
在原方案下:
    对单轴有:
        d = r - l ; s = r + l
        当 |d| < s * α 时,认为已正对 
    注意: 此时 光强与读数成反比,r | l 的读数反应"暗度"
    此时对步长的处理如下
        L = (0.4) * s / 4200 . 其中, 0.4 为步长系数,4200为手机光源距离10cm左右的读数标定.
    这里的问题在于:
    这个系统需要对步长进行单独计算,且更换光源时需要重新标定距离10cm处的读数,在多场景的应用中比较吃力.

对更改后的新方案:
    令:
        s' = 2 *(4090) - s; 用无光时的最大值作减法,使得 s' 正比于光强;
    定义比值:
        k = d / s'
    分类讨论:
    1° 无光时:    判断 s' -> 0;
    2° 防削顶:    单轴触底不可用时,忽略该刻的动作;
    3° 有光时
        k ∈ [-1,1]
        (i) |k| <= α 认为对准
        (ii) |k| > α 认为是未对准
    这里在保证两边都有光的小角度上,可以认为k∝偏差角度
    给定步长放大系数c,有 S_deg = c * k 
```

**更改已实施**  

这项更改在数学上类似将分母移向,将分式与2%作比较\.简化了对准判定条件和步长计算\.

\-02 **奇异点保护需要跟进** 

之前已经提到,atan2函数会在后转的角上留下奇异点\.这里的现象是,当横滚舵机转到0°或180°之外,俯仰舵机会失控乱动的问题,数学上的推导已进行,之前留着这个问题是为了演示数学现象\.现在为了机器的运转正常采取保护措施\.此处可将舵机的转角限定在 \[5,175\]°间,超出即冻结\.

**更改已实施** 

```C
if (yaw_target_f < GIMBAL_TARGET_MIN || yaw_target_f > GIMBAL_TARGET_MAX)
{
    return ;
}
```

#### 一些有趣的点回顾

\-01 **步长随光强变化的最终决定并非清汤寡水,而是厨师长在精心挑选厨具,几经波折后,大火收汁得到的**  

这个设计源于对一个bug的修改,中期测试发现:光源接近探头大约15cm的时候舵机头会突然左右上下摇摆,也就是产生了对齐\-\>出界\-\>再对齐\-\>再出界的现象\.

对这个bug的成因依次有如下猜想:

1\.设备问题\(这设备怎么这么坏啊?那我玩什么机器啊\)

一开始以为是自己的手电筒灯珠与室友不一样,想着索性不改,最后结论显而易见:

**人笨,不能怪刀钝** 

2\.信噪比不足

理论上当光越强,读数越低,\*2%后的容差越小,当容差小到框不住噪声的范围时,就会触发随机抖动\.

事实上,经过8次采样的滑动平均滤波后,噪声产生的影响几乎为零,把灯静止时读数可以正常保持\.

3\.容差太窄就硬加的雷霆操作

就刚才提到的而言,成因正确的话,把测量值加一个合适的常数可以改变这个问题,或者使用数学函数让容差下降地没那么快\.当然,路线错了就是浪费表情,白搞\.而且还会引入对准判定变松的附加问题\.

经过烧烤,最终发现bug的成因是光源靠近的时候使用统一步长会在微调时导致过冲,因此出现: 过冲\-\>纠正\-\>

再过冲\-\>再纠正 的情况\.

\-02 **前馈与轻量一阶低通滞后的奇妙平衡**

本身为了跟手感设计了前馈,又为了消除舵机在1°上的反复抖动将互补滤波复用并退化成一阶低通滤波\.结果测下来很跟手\.最后计算发现,前馈根本就没起作用,被一阶低通抵消了\.

前馈提前3刻,一阶低通系数0\.75平均滞后\(0\.75/\(1\-0\.75\)\)即3刻\.抵消

综合考虑到轻量一阶低通滤波可以消除舵机在1°上抖动的问题,整机在当前状态下能正常运行,决定不改,当作一个有趣的特性保留\.

## 想讨论的两个问题

### 01 数学推导和实践验证的取舍

诚然,物理的本质始终是"自然哲学的数学原理",物理规律要能由数学工具可描述可预测地确定,从数学运算/代数变形的角度探讨物理/工程是最深入且本质的东西\.但仍值得注意的是:实际的工程远比理想的物理模型更加复杂,实践和经验在这里的占比比较大,要更加深入地了解一个模块/元器件,必须要重视实践中它表现出来的效果\.

在这里,数学推导和实测验证从来不是对立的两面,它们是各有其美,相辅相成的,数学暴露出理论的深度和逻辑以及"大道至简"的真理为实验数据提供有力支撑;实践则展现直观的现象和效果以及易于理解的便捷反过来验证数学推导的合理性\.在工科学习中,必须要找到二者的平衡点\.
